Pillar philosophy

How to think about this pillar

This pillar governs the operational sequence of a curtailment event: what triggers it, who or what activates it, and how much notice the customer receives.

Design tutorial

Read the pillar as a design sequence

Treat curtailment as an auditable sequence: trigger → notice → execution. The design should make each step observable and implementable.

1. Define triggering events

State whether emergency, maintenance, congestion or another condition can activate the flexible limit.

2. Define activation mode

Clarify whether the system operator controls the action, local automation executes it, or the customer self-dispatches.

3. Define notification timing

Record the notice period and distinguish scheduled events from near-real-time or ex-post actions.

Key language

Terms to keep consistent

Use these short definitions consistently when comparing schemes or discussing this pillar.

Curtailment trigger

The event or network condition that authorises activation of the flexible restriction, such as emergency, maintenance or congestion.

Activation mode

How the curtailment instruction is physically implemented, for example by system-operator control, local automation or customer self-dispatch.

Curtailment notification

How far in advance the user is informed that a curtailment event will occur.

Real-time / near-real-time activation

Operational activation close to delivery, where notice and response occur within a short interval.

Partial limitation vs. disconnection

Curtailment can reduce available power to an agreed level or, where the framework allows, remove access completely for the event.

  3. Is activation mode truly independent of notification time, given that automated schemes generally allow shorter notice periods?
